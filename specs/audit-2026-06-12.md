# ProcSentinel — Security & Improvement Audit

**Date:** 2026-06-12
**Scope:** full codebase — `server/` (Go), `agent/` (Go), `mobile/` (Flutter), `dist/` (deployment artifacts), build scripts, specs.
**Method:** manual source review of every Go/Dart source file, deployment scripts, systemd/Docker configs, and Android manifest.

Severity scale: **Critical** (exploitable now, full compromise or fail-open), **High** (significant weakness, realistic abuse), **Medium** (hardening gap), **Low** (hygiene). `BUG-*` are correctness/reliability defects, `IMP-*` are improvements.

---

## Critical

### SEC-01 — Hardcoded fallback token in the repository, shared by both auth tiers
- **Where:** `server/middleware.go:35,39`, `agent/main.go:72`
- The literal token `mILp9n6shk3G9SGSaS2nmP6YlLHwsP1Z` is committed to the repo and used as the fallback for **both** `TOKEN` (client) and `ADMIN_TOKEN` (admin) whenever the env var is unset. Anyone who has ever seen the repo has full admin access to any server started without an explicit `.env`. Because the fallback is identical for both tiers, a client-level token is also an admin token on default installs.
- **Fix:** remove all fallbacks. Server must refuse to start unless both tokens are set, ≥16 chars, not placeholder values, and different from each other. Agent must error out when `TOKEN` is unset.

### SEC-02 — No transport encryption (HTTP only)
- **Where:** `server/main.go:83-89`, mobile default `http://192.168.1.10:8080` (`settings_service.dart:14`), `dist/server/server.env`
- Bearer tokens (including the admin token) travel in cleartext on every request. Any on-path observer on the LAN/Wi-Fi recovers the admin token from a single packet. Note: the Flutter app uses `dart:io` sockets, which bypass Android's cleartext-traffic policy, so HTTP silently works in release builds.
- **Fix:** add optional TLS to the server (`TLS_CERT`/`TLS_KEY` env vars → `ListenAndServeTLS`), document self-signed certificate generation, default new deployments to HTTPS.

### SEC-03 — Fail-open: unknown computers get `mode=free` on their first sync
- **Where:** `server/handlers.go:16-29`
- On `sql.ErrNoRows` the zero-value `blocked=false` is assigned to `isComputerBlocked`, so a computer never seen before receives `mode: "free"` (no enforcement) on its **first** sync — while `updateComputerDateTime` (`db.go:205-208`) simultaneously inserts the row with `blocked=1`. First response contradicts the stored default-deny. An agent that wipes the `computers` row (or uses a fresh identity each boot — see SEC-09) gets a free pass every time.
- **Fix:** treat `ErrNoRows` as `blocked=true` (default-deny), consistent with the insert.

## High

### SEC-04 — Placeholder tokens accepted; installer never generates real ones
- **Where:** `dist/server/server.env` (`TOKEN=your_token_here`), `dist/server/install.sh`
- `install.sh` copies `server.env` verbatim to `/usr/local/bin/guardian/.env`. If the operator forgets to edit it, the server happily runs with the guessable token `your_token_here` / `your_admin_token_here`. No `chmod`/`chown` is applied to the `.env` containing secrets.
- **Fix:** startup validation rejects placeholders (covered by SEC-01 fix); `install.sh` generates random tokens via `openssl rand` on first install and sets `.env` to mode `600`.

### SEC-05 — No rate limiting or brute-force protection
- **Where:** `server/routes.go` (no limiting middleware)
- Token guessing and request flooding are unthrottled. A 32-char token is not practically brute-forceable, but short operator-chosen tokens are, and unauthenticated flooding of `/health` or auth-failing endpoints is free.
- **Fix:** per-IP rate limiting middleware (e.g. `go-chi/httprate`).

### SEC-06 — Unbounded request bodies
- **Where:** all handlers in `server/handlers.go` (`json.NewDecoder(r.Body)` with no limit)
- A client can POST an arbitrarily large body; combined with `ReadTimeout=15s` this allows cheap memory-pressure DoS.
- **Fix:** `http.MaxBytesReader` middleware (1 MiB is generous for this API).

### SEC-07 — Server runs as root with zero sandboxing; Docker image also runs as root
- **Where:** `dist/server/guardian-server.service` (`User=root`, no hardening directives), `dist/server/Dockerfile` (no `USER`)
- A network-facing service that only needs to read one SQLite file runs as root, with the DB and secrets inside `/usr/local/bin/guardian/` (binaries directory used as state directory).
- **Fix:** dedicated `guardian` system user; state in `/var/lib/guardian`; systemd hardening (`NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`); non-root `USER` in the Dockerfile.

### SEC-08 — Agent blacklist mode can kill critical system processes and uses dangerous matching
- **Where:** `agent/main.go:285-295` (console), `agent/service_windows.go:189-198` (service), `agent/main.go:524-533` (`killProcess`)
- Three compounding problems:
  1. Blacklist mode does **substring matching against the entire raw `tasklist` CSV output** — an app name matches any column of any process line, not process names.
  2. The `isSystemProcess` guard is applied **only in whitelist mode**. A blacklist entry like `s` or `host` (typo or malice with a leaked client→admin token) matches and kills `svchost.exe`, `lsass.exe` (instant BSOD), or the agent itself.
  3. On Linux/macOS `killProcess` runs `pkill -f <name>`: the name is interpreted as a **regex against full command lines** — `.` matches everything; a single bad entry kills nearly every user process.
- **Fix:** match per extracted process name only; apply `isSystemProcess` in both modes; kill by exact extracted name (`taskkill /IM <exact>`, `pkill -x` with `regexp.QuoteMeta`); validate app names server-side (SEC-08a/IMP-02: charset `[A-Za-z0-9 ._-]`, length 3–64).

### SEC-09 — Computer identity is a spoofable plain integer; unbounded row creation
- **Where:** `server/handlers.go:12-29`, `agent/main.go:76-80` (`IDENTITY` from `.env`)
- Any holder of the (shared, see SEC-12) client token can sync with any `identity` value: (a) pick an identity known to be unblocked and receive `mode=free`; (b) sync with millions of distinct identities and grow the `computers` table without bound (every sync INSERTs).
- **Fix (design work, not in current plan):** pairing/registration flow with per-computer secrets, or HMAC-signed identities. Interim mitigations: SEC-03 fix (unknown ⇒ blocked) removes incentive (a); rate limiting (SEC-05) bounds (b).

### SEC-10 — Mobile app stores the admin token in plaintext SharedPreferences
- **Where:** `mobile/lib/services/settings_service.dart:35-49`
- `shared_preferences` writes an unencrypted XML readable on rooted devices and includable in ADB/auto backups. This token is full admin on the server.
- **Fix:** migrate to `flutter_secure_storage` (Android Keystore), with a one-time migration from the old store.

## Medium

### SEC-11 — CORS wildcard with Authorization header allowed
- **Where:** `server/routes.go:11-17` — `AllowedOrigins: ["*"]`. No browser frontend exists; the only clients are the Go agent and the Flutter app, neither of which needs CORS. Low practical impact (no cookies), but it invites a future browser UI to be built on an unsafe default. **Fix:** restrict via `ALLOWED_ORIGINS` env or drop the middleware.

### SEC-12 — One shared client token across all agents; no rotation mechanism
- Compromise of any single machine discloses the token for the whole fleet; rotating requires manually touching every `.env`. **Fix (future):** per-agent tokens issued at registration (pairs with SEC-09).

### SEC-13 — Agent state files written world-readable
- **Where:** `agent/main.go:374,494` — `whitelist.txt` and `sync.json` written `0644`. A local non-admin user can read them; on Unix installs (directory permitting) tampering with `whitelist.txt` exempts arbitrary processes from whitelist enforcement. **Fix:** `0600`, and document that the agent directory must be admin-writable only.

### SEC-14 — Agent installs under `C:\Windows\System32\ProcSentinel`
- **Where:** `dist/agent/bin/Install-Agent64.ps1:6`
- System32 is the wrong location for third-party services and is subject to WOW64 filesystem redirection for 32-bit processes (the 32-bit installer's path silently maps to `SysWOW64`). **Fix:** `%ProgramFiles%\ProcSentinel\Agent`.

## Low

- **SEC-15** — `getLocalIP()` dials `8.8.8.8:80` (`server/helpers.go:35`): outbound dependency just to discover the local IP; fails closed to interface enumeration anyway.
- **SEC-16** — `/info` hardcodes `ServerPort: "8080"` and `Version: "1.0.0"` (`server/handlers.go:318-324`) regardless of actual config.
- **SEC-17** — Agent `loadEnvFile` overrides already-set process env vars (`agent/main.go:57`), unlike the server which respects them (`server/helpers.go:77`); inconsistent precedence.

## Correctness / reliability bugs

### BUG-01 — Data race on the shared sync state pointer in the agent
- **Where:** `agent/main.go:109-129,219-222` and `agent/service_windows.go:124-127,225-258`
- The `**SyncResponse` pointer is written by the sync goroutine and read by the monitor loop with no synchronization — a data race under the Go memory model (`go test -race` would flag it). **Fix:** `atomic.Pointer[SyncResponse]`.

### BUG-02 — `PUT /status` with a missing `enabled` field silently disables enforcement
- **Where:** `server/handlers.go:276-299` — `Enabled bool` decodes absent field as `false`. A client that sends only `{"mode":"whitelist"}` turns the whole system off. **Fix:** `Enabled *bool`, only apply when present.

### BUG-03 — `PUT /manage/computers` destroys the last-seen timestamp
- **Where:** `server/handlers.go:400` — `INSERT OR REPLACE` rewrites the row, resetting `datetime` to "now"; an admin block/unblock action falsifies last-seen data. **Fix:** `ON CONFLICT(identity) DO UPDATE SET blocked = excluded.blocked`.

### BUG-04 — SQLite opened with no WAL / busy timeout
- **Where:** `server/db.go:9-15` — default `journal_mode` and zero busy timeout with concurrent handler writes risks `database is locked` errors. **Fix:** DSN pragmas `journal_mode(WAL)`, `busy_timeout(5000)`; `SetMaxOpenConns(1)`.

### BUG-05 — Power-off command is ignored when the blacklist is empty
- **Where:** `agent/main.go:255-268`, `agent/service_windows.go:162-173`
- The loop `continue`s on "no applications and not whitelist" **before** checking the `power` client entry, so remote shutdown silently does nothing unless at least one app is blacklisted. **Fix:** check `power` before the empty-list short-circuit.

### BUG-06 — Dead/redundant code
- `removeApplicationFromDatabase` (`server/db.go:185-188`) is never called; `handleUpdateApplication` checks cache existence twice (`handlers.go:170-177`); mode-less update picks an arbitrary entry via map iteration order (non-deterministic when both modes exist for one name).

## Improvements

- **IMP-01 — No automated tests at all.** Highest-leverage improvement; the plan bootstraps an `httptest`-based suite for the server and unit tests for agent matching logic.
- **IMP-02 — Server-side application-name validation** (charset/length) — also a safety net for SEC-08.
- **IMP-03 — Audit logging of admin actions** with remote address (partially present; make uniform).
- **IMP-04 — Naming drift:** "Guardian" vs "ProcSentinel" across binaries (`guardian-server`), services (`guardian.service` vs `guardian-server.service` vs `ProcSentinelAgent`), docs (CLAUDE.md claims `procsentinel-server.tar.gz`; `build.sh` produces `guardian-server` and the tar step is commented out). Pick one name; sync docs with reality.
- **IMP-05 — Agent sync has no backoff/jitter;** a fleet hammers a recovering server in lockstep.
- **IMP-06 — `/info` should derive port/version from actual configuration** (see SEC-16).
- **IMP-07 — Mobile "Test connection" gives false confidence:** it calls unauthenticated `/health` (`settings_service.dart:70-97`), so a wrong admin token still shows "connected". Probe `/status` instead. More broadly, all mobile service methods swallow errors into defaults — a 401 is indistinguishable from an empty list.

## Mobile UI/UX findings (Android app "Guardian")

Reviewed: `main.dart`, all four screens, `snackbar_helper.dart`, against the parent-managing-kids'-computers persona.

### BUG-07 — Online status is wrong in every non-UTC timezone
- **Where:** `computers_screen.dart:255-268` (`_isComputerOnline`), `:270-286` (`_formatLastSeen`)
- SQLite `CURRENT_TIMESTAMP` values arrive as `"2026-06-12 08:15:00"` — UTC but with **no timezone marker**, so `DateTime.parse` treats them as **local** time. The server's `current_time` *does* carry an offset and parses correctly. The comparison is therefore skewed by the full UTC offset: at UTC+3 every computer shows "offline" permanently (60s threshold vs 3h skew), and "Last seen" times are wrong by the same offset. The core feature of the Computers screen does not work outside UTC.
- **Fix:** parse naive server timestamps as UTC (append `Z`), then `toLocal()` for display.

### UX-01 — Redundant polling and double round-trips everywhere
- `main.dart:65-67` polls `testConnection` + `getClientData` every 10s for the nav-bar icons; `computers_screen.dart:30-32` runs its own always-on 10s timer (even when the tab is hidden — `IndexedStack` keeps it alive); every screen's `_loadData` calls `testConnection` *before* the real requests, doubling latency and request count. No shared state/cache between screens. **Fix (future design):** one polling repository all screens subscribe to; pause when backgrounded.

### UX-02 — Every refresh blanks the screen with a full-page spinner
- All three data screens set `_isLoading = true` at the top of `_loadData`, replacing live content with a `CircularProgressIndicator` — including on settings-listener triggers and the app-bar refresh button. Content flashes away on every poll-driven reload. **Fix:** full-screen spinner only on first load; keep stale content during refreshes (RefreshIndicator already exists).

### UX-03 — Wrong token is indistinguishable from "server offline"
- All `SettingsService` methods swallow errors into defaults (`[]`, `false`), so a 401 renders as "Server Not Connected" or an empty list. A parent who mistypes the token gets no hint that auth — not the network — is the problem. (The `_buildDisconnected` widget is also copy-pasted three times.) **Fix:** connection check returns connected/unauthorized/unreachable; shared disconnected view says "check your token" when it's a 401.

### UX-04 — The two most destructive controls are casual one-tap toggles
- The shield icon (disables **all enforcement fleet-wide**) is a single unconfirmed tap, duplicated in three app bars with copy-pasted handlers.
- The Blacklist/Whitelist `SegmentedButton` switches mode with one tap and no confirmation — switching to whitelist with an incomplete list starts killing every unlisted process on every machine (compare: "Remove All" *does* confirm).
- Additionally, `_setMode` (`home_screen.dart:317`) re-sends the *cached* `enabled` value alongside the mode — the client-side twin of BUG-02: a stale cache silently toggles enforcement. After the server-side BUG-02 fix, the app should send a mode-only payload.

### UX-05 — Snackbars: 1-second duration and raw exception dumps
- `snackbar_helper.dart:7` defaults every message to 1 second — errors are unreadable (and hostile to TalkBack users). Several call sites show raw Dart exceptions (`'Error loading data: $e'`), e.g. a full `SocketException` string. **Fix:** ~4s for errors, human-readable messages.

### UX-06 — Add-application flow fights the user
- `home_screen.dart:124-141`: the bottom sheet **closes before validating**, so an empty/duplicate name shows a snackbar after the sheet is gone and the user must reopen and retype. Server error details (which will carry validation messages after IMP-02) are discarded — `addBlockedApplication` returns only `bool`, so everything becomes "Failed to add application". Success shows no feedback at all (remove shows a green snackbar — inconsistent). **Fix:** validate inline in the sheet, surface the server's error text, confirm success.

### UX-07 — Computers are unnameable
- "Computer #3" is all a parent ever sees. No way to label machines ("Kids' room PC"). Requires a `name` column on `computers` plus API/UI — future design work, but the single biggest practical usability gap.

### UX-08 — Online threshold contradicts the shipped agent config
- `_isComputerOnline` uses a 60s window, but `dist/agent/agent.env` ships `CHECK_INTERVAL=30`: one missed poll and a healthy machine flickers "offline"; any interval >60s shows it offline permanently. **Fix:** ~90s threshold (tolerates one missed 30s poll), documented relative to `CHECK_INTERVAL`.

### UX-09 — Interaction polish
- System screen tiles are `GestureDetector` on a `Card` — no ripple, no pressed feedback, nothing indicating they're tappable (`system_screen.dart:210`).
- The per-computer `Switch` means **ON = blocked** — inverted from platform convention (on = active/allowed) with no label clarifying it.
- Token field has no show/hide toggle (`settings_screen.dart:214`) — long tokens must be typed blind; Test and Save share one `_isSaving` flag so both spin together.

### UX-10 — No dark theme, no localization, hardcoded US time format
- Light-only `ThemeData` (Material 3 `darkTheme`/`themeMode: system` is nearly free); all strings hardcoded English; `_formatLastSeen` hand-rolls 12-hour AM/PM regardless of device locale (most of Europe uses 24h).

### UX-11 — App list sorts disabled entries first
- `home_screen.dart:24-28`: enabled apps sort *after* disabled ones. If intentional ("needs attention first") it deserves a comment; if not, it reads as a bug — active blocks are what a parent scans for.

### UX-12 — Accessibility
- No `Semantics` labels on switches ("Block computer 3"), color-only online dot, 1s snackbars (see UX-05). Low priority for a single-user tool, but cheap to fix alongside other work.
